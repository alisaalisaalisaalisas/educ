## 📊 2. Zabbix & Nagios: Роль и логика работы (Поверхностный обзор)

Интервьюеру **не нужны** тонкости написания кастомных C-модулей для Zabbix. Достаточно четко и уверенно понимать **зачем они нужны и как устроена цепочка оповещения**.

### Зачем нужны Zabbix / Nagios:
Это классические системы **инфраструктурного мониторинга серверов, виртуальных машин, сетевого оборудования (коммутаторы, маршрутизаторы) и физического железа (диски, температура, вентиляторы)**.

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│ Target Host  │ ──► │ Zabbix Agent │ ──► │ Zabbix Server│ ──► │  Trigger &   │
│ (Linux/Win)  │     │   or SNMP    │     │  (Database)  │     │  Alert Rule  │
└──────────────┘     └──────────────┘     └──────────────┘     └──────┬───────┘
                                                                      │
                                                                      ▼
                                                              ┌───────────────┐
                                                              │  Уведомление  │
                                                              │ (Telegram/SMS)│
                                                              └───────────────┘
```

### Основные компоненты Zabbix:
1. **Zabbix Agent:** Легковесный бинарник, установленный на целевом сервере. Собирает метрики (загрузка CPU, RAM, остаток диска, статус процессов).
2. **SNMP:** Протокол опроса сетевого оборудования (роутеры, свитчи) без установки агента.
3. **Item (Элемент данных):** Конкретная метрика, которую собирает сервер (например, `system.cpu.util`).
4. **Trigger (Триггер):** Логическое условие ошибки. Если условие истинно — триггер переходит в статус `PROBLEM` (авария).
5. **Action / Notification (Действие):** Отправка алерта дежурному в Telegram, Jira, PagerDuty или вызов скрипта самовосстановления.

### Типовые примеры триггеров Zabbix:
* `CPU utilization > 90% for 5m` (Высокая нагрузка процессора)
* `Available memory < 10%` (Риск OOM-Killer)
* `Free disk space on / < 15%` (Заканчивается место на корневом разделе)
* `Service nginx is not running` (Упал веб-сервер)
* `Host is unreachable by ping (loss > 20%)` (Сервер потерял сетевую связность)

> 💬 **Как отвечать на собеседовании:**
> *«С Zabbix/Nagios знаком на уровне эксплуатации: ориентируюсь в веб-интерфейсе, умею анализировать полученные алерты (высокий CPU, нехватка диска, недоступность хоста), проверять графики метрик и действовать по регламенту Runbook. При необходимости могу установить Zabbix Agent на сервер и проверить его статус через `systemctl status zabbix-agent`»*.

## 🪵 3. Стек ELK (Elasticsearch, Logstash, Kibana): Поверхностный обзор

Если на собеседовании заходит разговор о централизованном логировании — важно четко разделять роли трех компонентов.

```
┌─────────────────┐
│ Application Logs│
│   (/var/log/*)  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ Filebeat / Alloy│  (Агент: быстро читает файлы логов и отправляет дальше)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│    Logstash     │  (Конвейер: принимает, парсит структуру (Grok/JSON), фильтрует)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Elasticsearch  │  (База данных: распределенное полнотекстовое хранилище JSON)
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│     Kibana      │  (Веб-интерфейс: поиск логов (KQL), графики, построение дашбордов)
└─────────────────┘
```

### За что отвечает каждый компонент:
* **Elasticsearch:** Распределенная документоориентированная поисковая NoSQL база данных (хранилище). Хранит логи в виде JSON-документов и позволяет за миллисекунды выполнять полнотекстовый поиск по миллионам записей.
* **Logstash:** Тяжелый ETL-сервер (Extract, Transform, Load). Принимает сырые текстовые логи, парсит их с помощью регулярных выражений (**Grok-шаблонов**), разбивает на поля (`ip`, `status_code`, `response_time`) и складывает в Elasticsearch.
* **Filebeat:** Легковесный агент от Elastic (написан на Go), который ставится прямо на серверы приложений, «хвостит» файлы логов (`tail -f`) и пересылает их в Logstash или напрямую в Elasticsearch.
* **Kibana:** Веб-панель для людей. В ней дежурный инженер вбивает поисковые запросы по языку **KQL (Kibana Query Language)**, фильтрует ошибки по полям (например, `service.name: "auth" AND http.response.status_code >= 500`) и смотрит распределение ошибок по времени.

> 💬 **Как отвечать на собеседовании:**
> *«С ELK работал со стороны пользователя: использую Kibana для расследования инцидентов. Нахожу нужные записи по `trace_id`, `correlation_id` или подстроке `"ERROR"`, отфильтровываю логи конкретного сервиса по временному окну аварии и анализирую стектрейсы ошибок. Глубоким кластерным администрированием шардов (shards/replicas) Elasticsearch не занимался»*.

## 🔍 5. ТОП-4 Алгоритма Траблшутинга (Ключевой блок собеседования!)

На собеседованиях почти всегда дают практические задачи вида: *«Пользователи жалуются на проблему X. Твои действия?»*.

---

### Сценарий 1: «Сайт / API недоступен» (User Reports: Site is Down)

```
[ 1. DNS ] ────────► [ 2. Ping / Route ] ───► [ 3. Порты & Firewall ]
    dig / hosts          ping / traceroute        nc -zv / ss -tulpn
                                                          │
┌─────────────────────────────────────────────────────────┘
▼
[ 4. Nginx / Web ] ──► [ 5. Backend Service ] ──► [ 6. Ресурсы & Логи ]
    nginx -t / log         systemctl status           top / df / journalctl
```

#### Пошаговый алгоритм ответа (озвучивать по пунктам):
1. **Проверяю DNS:**
   - Резолвится ли имя сайта в IP-адрес: `dig +short example.com` или `nslookup example.com`.
2. **Проверяю сетевую доступность сервера:**
   - Пингуется ли IP: `ping -c 3 <IP>`. Если не пингуется — смотрю трассировку: `traceroute -n <IP>` (или `mtr`).
3. **Проверяю доступность TCP-порта снаружи:**
   - Открыт ли порт 80 / 443: `nc -zv <IP> 443` или `curl -Iv https://example.com`.
4. **Подключаюсь по SSH на сервер и проверяю веб-сервер:**
   - Жив ли Nginx: `systemctl status nginx`.
   - Валиден ли конфиг: `nginx -t`.
   - Слушает ли Nginx порты: `ss -tulpn | grep -E ':(80|443)'`.
   - Смотрю свежие ошибки: `tail -n 50 /var/log/nginx/error.log`.
5. **Проверяю сервис приложения (бэкенд):**
   - Статус процесса: `systemctl status backend-app` (или `docker ps`).
   - Логи службы: `journalctl -u backend-app -n 50 --no-pager`.
   - Доступен ли бэкенд локально: `curl -I http://127.0.0.1:8080/health`.
6. **Проверяю системные ресурсы сервера:**
   - Память и CPU: `top` или `htop` (нет ли 100% утилизации или зависших процессов).
   - Дисковое пространство: `df -h` и inodes: `df -i`.
   - OOM-Killer ядра: `dmesg -T | grep -i oom` (не убило ли бэкенд ядро).
7. **Проверяю базу данных и внешние зависимости:**
   - Доступна ли БД: `pg_isready -h localhost -p 5432`.

---

### Сценарий 2: «Диск заполнен на 100% (No space left on device)»

#### Пошаговый алгоритм ответа:
1. **Определяю переполненный раздел:**
   ```bash
   df -h
   ```
2. **Проверяю Inodes (Индексные дескрипторы):**
   ```bash
   df -i
   ```
   > ⚠️ Место в байтах может быть свободно, но если закончились **inodes** (миллионы мелких файлов сессий/писем), создание любого нового файла завершится ошибкой *No space left on device*!
3. **Ищу самые тяжелые директории и файлы:**
   ```bash
   du -sh /* 2>/dev/null | sort -hr | head -n 10
   du -sh /var/log/* 2>/dev/null | sort -hr | head -n 10
   ```
4. **Проверяю файлы, удаленные через `rm`, но удерживаемые процессами:**
   ```bash
   lsof | grep deleted
   ```
   > ⚠️ Если процесс пишет в лог, а вы сделали `rm log.txt`, диск **не освободится**, пока процесс не закроет дескриптор!
5. **Безопасная очистка:**
   * Обнуление тяжелого лога без удаления файла:
     ```bash
     truncate -s 0 /var/log/heavy_app.log
     ```
   * Очистка системных журналов systemd:
     ```bash
     journalctl --vacuum-time=2d
     ```
   * Очистка неиспользуемых Docker-слоев:
     ```bash
     docker system prune -f
     ```

---

### Сценарий 3: «Сервис не запускается (Failed to start)»

#### Пошаговый алгоритм ответа:
1. **Проверяю статус и код завершения:**
   ```bash
   systemctl status <service_name>
   ```
2. **Читаю детальные логи ошибки службы:**
   ```bash
   journalctl -u <service_name> -e --no-pager -n 50
   ```
3. **Проверяю синтаксис конфигурационных файлов:**
   * Для Nginx: `nginx -t`
   * Для SSH: `sshd -t`
   * Для Apache: `apachectl configtest`
4. **Проверяю занятость рабочего порта (Port Conflict):**
   ```bash
   ss -tulpn | grep :<port_number>
   ```
   * Если порт уже занят другим зависшим процессом — сервис не сможет сделать `bind()`.
5. **Проверяю права доступа (Permissions):**
   * Может ли пользователь службы читать конфигурацию и писать в `/var/log/<service>`:
   ```bash
   ls -la /etc/<service>/
   ls -ld /var/log/<service>/
   ```
6. **Проверяю зависимости:**
   * Доступна ли база данных, DNS, смонтирован ли диск с данными.

---

### Сценарий 4: «API возвращает 502 Bad Gateway»

#### Архитектурная суть:
```
[ Клиент / Браузер ] ──(HTTP)──► [ Nginx (Reverse Proxy) ] ──(Connection Refused / Crash)──► [ Backend App (8080) ]
                                          │
                                          ▼
                               Возвращает 502 Bad Gateway
```

#### Пошаговый алгоритм ответа:
1. **Понимаю суть ошибки:** Nginx (шлюз) попытался проксировать запрос на бэкенд, но бэкенд либо выключен, либо сбросил соединение, либо упал.
2. **Смотрю лог ошибок Nginx:**
   ```bash
   tail -n 50 /var/log/nginx/error.log
   ```
   * `connect() failed (111: Connection refused)` ➔ Бэкенд не запущен или слушает другой порт.
   * `no live upstreams while connecting to upstream` ➔ Все реплики бэкенда недоступны.
   * `Permission denied while connecting to upstream` ➔ Проблема прав доступа к Unix-сокету (`.sock`).
3. **Проверяю процесс бэкенда:**
   ```bash
   systemctl status backend-app
   docker ps | grep backend
   ```
4. **Проверяю OOM-Killer:**
   ```bash
   dmesg -T | grep -i oom | tail -n 10
   ```
5. **Тестирую бэкенд локально напрямую в обход Nginx:**
   ```bash
   curl -Iv http://127.0.0.1:8080/health
   ```
6. **Перезапускаю бэкенд и проверяю стабилизацию:**
   ```bash
   systemctl restart backend-app
   ```

## 🚩 6. Полный справочник флагов утилит командной строки (Must-Know Flags)

На собеседованиях регулярно просят объяснить конкретные комбинации ключей: *«Что делает `ps aux`? Зачем флаг `-n` в `ss`? Чем отличается `tail -f` от `tail -F`?»*.

---

### 🌐 1. `curl` (Швейцарский нож HTTP-запросов)

| Флаг | Полное имя | Зачем нужен и что делает |
| :--- | :--- | :--- |
| **`-I`** / **`--head`** | Head only | Запрашивает **только HTTP-заголовки ответа** без скачивания тела (быстрая проверка 200/404/502). |
| **`-v`** / **`--verbose`** | Verbose | Подробный вывод: DNS-резолвинг, TCP handshake, TLS-сертификаты, отправленные и полученные заголовки. |
| **`-s`** / **`--silent`** | Silent mode | Отключает вывод прогресс-бара и ошибок (идеально для Bash-скриптов). |
| **`-L`** / **`--location`** | Follow redirects | Автоматически переходить по HTTP-редиректам (301 Moved Permanently / 302 Found). |
| **`-k`** / **`--insecure`** | Insecure SSL | Игнорировать ошибки самоподписанных (self-signed) или просроченных SSL-сертификатов. |
| **`-X`** | Request method | Указать HTTP-метод: `curl -X POST`, `curl -X DELETE`, `curl -X PUT`. |
| **`-H`** | Header | Передать кастомный HTTP-заголовок: `curl -H "Authorization: Bearer token" -H "Content-Type: application/json"`. |
| **`-d`** | Data | Передать тело POST-запроса (строку или JSON): `curl -d '{"user":"admin"}'`. |
| **`-u`** | User credentials | Передать логин и пароль для Basic Auth: `curl -u admin:secret123`. |
| **`-o`** / **`-O`** | Output file | `-o file.zip` (сохранить с указанным именем), `-O` (сохранить с оригинальным именем из URL). |
| **`--connect-timeout`** | Timeout in seconds | Максимальное время ожидания TCP-подключения к серверу: `curl --connect-timeout 5`. |
| **`-w`** | Write out format | Вывести кастомные метрики (например, время ответа): `curl -w "%{time_total}\n" -o /dev/null -s https://api.com`. |

### 🔌 2. `ss` и `netstat` (Сетевые сокеты и порты)

> 💡 **Золотая комбинация дежурного инженера:** `ss -tulpn`

| Флаг | Значение | Описание |
| :--- | :--- | :--- |
| **`-t`** | TCP | Показать только **TCP** сокеты. |
| **`-u`** | UDP | Показать только **UDP** сокеты. |
| **`-l`** | Listening | Показать только **слушающие** порты (серверы, ожидающие входящих соединений). |
| **`-p`** | Processes | Показать **имя процесса и PID**, открывшего порт (требует `sudo`). |
| **`-n`** | Numeric | **Не резолвить имена хостов и портов** через DNS (выводить `127.0.0.1:80` вместо `localhost:http`). Работает мгновенно без зависаний! |
| **`-a`** | All | Показать все сокеты (и слушающие, и установленные `ESTABLISHED`). |

---

### ⚙️ 3. `ps` (Процессы операционной системы)

> 💡 **Золотые комбинации:** `ps aux` и `ps -ef`

| Флаг / Комбинация | Что означает каждая буква |
| :--- | :--- |
| **`ps aux`** | • **`a`** — показать процессы всех пользователей.<br>• **`u`** — формат с подробной информацией (пользователь, `%CPU`, `%MEM`, время старта).<br>• **`x`** — включить процессы без управляющего терминала (демоны, системные службы). |
| **`ps -ef`** | • **`-e`** (every) — показать абсолютно все процессы.<br>• **`-f`** (full) — полный формат вывода (включая PPID — идентификатор родительского процесса). |
| **`--sort=-%mem`** | Сортировка по убыванию использования оперативной памяти: `ps aux --sort=-%mem \| head -n 10`. |
| **`--sort=-%cpu`** | Сортировка по убыванию использования CPU: `ps aux --sort=-%cpu \| head -n 10`. |

### 💾 4. `df` и `du` (Дисковое пространство)

| Утилита / Флаг | Значение | Зачем используется |
| :--- | :--- | :--- |
| **`df -h`** | Human-readable | Показывает остаток места на смонтированных разделах в гигабайтах/мегабайтах (G/M). |
| **`df -i`** | Inodes | Показывает процент использования **индексных дескрипторов** (inodes). |
| **`df -T`** | Type | Выводит тип файловой системы (`ext4`, `xfs`, `btrfs`, `tmpfs`, `overlay`). |
| **`du -s`** | Summary | Выводит только итоговый размер указанной папки без перечисления подкаталогов. |
| **`du -h`** | Human-readable | Размеры файлов в удобном формате (K, M, G). |
| **`du -a`** | All | Считать и папки, и отдельные файлы. |
| **`--max-depth=1`** | Depth limit | Ограничить глубину обхода только первым уровнем вложенности: `du -h --max-depth=1 /var`. |
| **`du -sh /* 2>/dev/null \| sort -hr`** | Комбинация | Найти топ самых тяжелых папок на сервере, заглушив ошибки доступа. |

### 📜 5. `journalctl` (Чтение системных логов systemd)

| Флаг | Значение | Зачем используется |
| :--- | :--- | :--- |
| **`-u <unit>`** | Unit | Читать логи конкретной службы: `journalctl -u nginx`. |
| **`-e`** | End | Сразу перейти в самый **конец журнала** к последним событиям. |
| **`-f`** | Follow | Режим реального времени (стриминг новых строк, аналог `tail -f`). |
| **`-n <N>`** | Number | Количество последних строк: `journalctl -u nginx -n 50`. |
| **`--since`** | Time filter | Фильтр по времени: `journalctl --since "1 hour ago"` или `journalctl --since "2026-08-19 03:00"`. |
| **`-p err`** | Priority | Фильтр по уровню важности: `journalctl -p err..emerg` (показать только `Error`, `Critical`, `Alert`). |
| **`--no-pager`** | No pager | Вывести весь текст в stdout сразу без запуска утилиты `less` (удобно для grep). |
| **`--vacuum-time=2d`** | Clean old logs | Удалить журналы старше 2 дней для освобождения диска. |

### 📡 11. `ping`, `traceroute`, `dig`, `lsof`, `tail`, `free`

* **`ping -c 4 8.8.8.8`:** отправить ровно 4 ICMP-пакета (флаг `-c` = count).
* **`traceroute -n 1.1.1.1`:** трассировка маршрута без DNS-резолвинга IP-адресов узлов (`-n` предотвращает зависания).
* **`dig +short example.com`:** быстрый DNS-запрос, возвращающий только IP-адрес.
* **`dig +trace example.com`:** полная итеративная трассировка DNS от корневых серверов (Root DNS `.`) до авторитетных.
* **`lsof -i :8080`:** узнать, какой конкретно процесс (и PID) слушает порт 8080.
* **`tail -f /var/log/app.log`:** читать новые строки файла в реальном времени.
* **`tail -F /var/log/app.log`:** читать в реальном времени с автоматическим переоткрытием файла при ротации логов (logrotate).
* **`free -m` / `free -h`:** оперативная память в мегабайтах / удобном формате (строка `available` показывает реально доступную память с учетом buff/cache).

## 🎯 7. Имитация собеседования (Mock Interview: 25 блиц-вопросов)

Используйте этот блок для самопроверки. Закрывайте ответы рукой и пробуйте сформулировать ответ вслух за 30 секунд.

---

### 🐧 Блок 1: Linux & Система

#### 1. Чем Load Average (LA) отличается от загрузки CPU (%CPU)?
> **Ответ:** `%CPU` показывает процент времени, когда процессор занят вычислениями. **Load Average** — это средняя длина очереди задач в состояниях `R` (Running) и `D` (Uninterruptible Sleep — ожидание дискового ввода-вывода). LA может быть высоким при низком CPU, если сервер уперся в медленный диск (`iowait`).

#### 2. Что делать, если при попытке создать файл система пишет "No space left on device", хотя `df -h` показывает 50 Гб свободного места?
> **Ответ:** Закончились свободные **inodes** (индексные дескрипторы) из-за огромного количества мелких файлов. Проверяется командой `df -i`. Решение: найти каталоги с миллионами файлов и очистить их.

#### 3. Вы удалили лог `rm /var/log/app.log`, но свободное место по `df -h` не прибавилось. Почему?
> **Ответ:** Файловый дескриптор всё еще открыт работающим процессом приложения. Поиск: `lsof \| grep deleted`. Решение: обнулить лог через `truncate -s 0` или перезапустить сервис (`systemctl reload`).

#### 4. В чем разница между `kill -15` (SIGTERM) и `kill -9` (SIGKILL)?
> **Ответ:** `SIGTERM (15)` — сигнал вежливого завершения (Graceful Shutdown), процесс может перехватить его и закрыть соединения. `SIGKILL (9)` — принудительное немедленное уничтожение процесса ядром без сохранения состояния.

#### 5. Что такое Зомби-процесс (`Z`) и как его убрать?
> **Ответ:** Зомби — дочерний процесс, который завершил работу, но родительский процесс еще не прочитал его код завершения через вызов `wait()`. Зомби нельзя убить через `kill -9` (он уже мертв). Нужно отправить сигнал `kill -CHLD` родительскому процессу или перезапустить родительский процесс.

#### 6. Что такое процесс в состоянии `D` (Uninterruptible Sleep)?
> **Ответ:** Процесс, зависший в системном вызове ядра при ожидании ответа от аппаратного диска или NFS-шары. Не реагирует даже на `kill -9`. Выходит из этого состояния только после ответа устройства или при перезагрузке ОС.

#### 7. Что означает код ошибки контейнера `Exit Code 137`?
> **Ответ:** Процесс был убит сигналом `SIGKILL (9)` со стороны **OOM-Killer** ядра Linux из-за превышения лимита оперативной памяти (`128 + 9 = 137`).

#### 8. Зачем нужен флаг `-n` в командах `ss -tulpn` или `traceroute -n`?
> **Ответ:** Отключает DNS-резолвинг IP-адресов в доменные имена и портов в названия сервисов. Предотвращает зависание утилиты при недоступности DNS-серверов.

### 🌐 Блок 2: Сети & Веб-серверы

#### 9. Что происходит по шагам при открытии `https://google.com` в браузере?
> **Ответ:**
> 1. DNS-резолвинг (получение IP-адреса).
> 2. TCP 3-Way Handshake (`SYN` ➔ `SYN-ACK` ➔ `ACK`) на порт 443.
> 3. TLS Handshake (проверка сертификата, согласование сессионного ключа шифрования).
> 4. Отправка HTTP-запроса `GET / HTTP/2`.
> 5. Обработка веб-сервером/бэкендом и возврат HTTP-ответа (`200 OK`).
> 6. Отрисовка страницы браузером.

#### 10. В чем разница между ошибками 502 Bad Gateway и 504 Gateway Timeout?
> **Ответ:**
> * `502 Bad Gateway`: Nginx не смог подключиться к бэкенду (бэкенд упал, порт закрыт, connection refused).
> * `504 Gateway Timeout`: Nginx успешно подключился, но бэкенд завис на тяжелом вычислении/SQL-запросе и не ответил за отведенный таймаут (`proxy_read_timeout`).

#### 11. Чем `TIME_WAIT` отличается от `CLOSE_WAIT` в TCP?
> **Ответ:**
> * `TIME_WAIT` — нормальное состояние сокета на стороне, закрывшей соединение (ждет 2×MSL для отлова запоздавших пакетов).
> * `CLOSE_WAIT` — ошибка в коде: удаленная сторона закрыла сокет, а локальное приложение забыло вызвать `close()`, что ведет к утечке файловых дескрипторов.

#### 12. Как быстро проверить доступность удаленного порта без telnet?
> **Ответ:**
> * `nc -zv 192.168.1.10 443`
> * `curl -Iv https://192.168.1.10:443`
> * `timeout 2 bash -c '</dev/tcp/192.168.1.10/443'`

### 📊 Блок 3: Мониторинг, Логи и Процессы

#### 13. Чем Pull-модель сбора метрик отличается от Push?
> **Ответ:**
> * **Pull (Prometheus):** Сервер мониторинга сам регулярно опрашивает (scrape) эндпоинты `/metrics` на серверах. Сервер контролирует нагрузку и сразу видит недоступность хоста.
> * **Push (Zabbix Trapper, StatsD):** Агенты сами шлют метрики на сервер. Удобно для кратковременных задач (Cron/Serverless).

#### 14. Что такое 4 Золотых Сигнала мониторинга (Google SRE Golden Signals)?
> **Ответ:** **Latency** (Задержка), **Traffic** (Трафик/RPS), **Errors** (Ошибки), **Saturation** (Насыщение ресурсов CPU/RAM/IO).

#### 15. Чем Counter отличается от Gauge в Prometheus?
> **Ответ:**
> * `Counter`: монотонно растущий счетчик (сбрасывается только при рестарте, анализируется через `rate()`). Пример: количество запросов.
> * `Gauge`: датчик мгновенного значения, которое может как расти, так и падать. Пример: свободная память, температура.

#### 16. Зачем нужен стек ELK и из чего он состоит?
> **Ответ:** Для централизованного сбора и поиска по текстовым логам. **Logstash** (или Filebeat) собирает и парсит логи, **Elasticsearch** сохраняет и индексирует для быстрого поиска, а **Kibana** предоставляет веб-интерфейс для фильтрации и дашбордов.

#### 17. В чем разница между `systemctl restart` и `systemctl reload`?
> **Ответ:** `restart` полностью гасит и заново запускает процесс с кратковременным разрывом соединений. `reload` перечитывает конфигурационные файлы без остановки процесса (Graceful/Zero-Downtime).

#### 18. Как посмотреть только последние 50 строк лога службы с фильтрацией по слову ERROR?
> **Ответ:**
> ```bash
> journalctl -u my-service -n 50 --no-pager | grep -i "error"
> ```

#### 19. Как найти на сервере 5 самых больших файлов?
> **Ответ:**
> ```bash
> find / -type f -exec du -h {} + 2>/dev/null | sort -hr | head -n 5
> ```

#### 20. В чем разница между SLI, SLO и SLA?
> **Ответ:**
> * **SLI (Indicator):** факт метрики качества (например: 99.8% успешных ответов).
> * **SLO (Objective):** внутренняя цель команды (например: держать доступность не ниже 99.9%).
> * **SLA (Agreement):** юридический договор с клиентом с финансовыми штрафами за нарушение.

### 🚨 Блок 4: Ситуационные кейсы (Incident Troubleshooting)

#### 21. КЕЙС: Пришел алерт: «Nginx 502 Bad Gateway на проде в 03:00 ночи». Первые 3 действия?
> **Ответ:**
> 1. Проверяю `tail -n 50 /var/log/nginx/error.log` (выясняю, на какой upstream IP:порт ругается Nginx).
> 2. Проверяю статус процесса бэкенда (`systemctl status backend` или `docker ps`) и dmesg на OOM-Killer (`dmesg -T \| grep -i oom`).
> 3. Если процесс упал — перезапускаю (`systemctl restart backend`), проверяю ответ через `curl -I http://127.0.0.1:8080/health` и фиксирую инцидент в Jira.

#### 22. КЕЙС: Разработчик говорит: «Я залил конфиг, но сервис не поднимается». Как помочь?
> **Ответ:**
> 1. Выполняю `journalctl -u <service> -e --no-pager` для чтения стектрейса ошибки старта.
> 2. Проверяю синтаксис конфига встроенным валидатором (`nginx -t` и т.д.).
> 3. Проверяю права доступа на конфигурационные файлы (`chmod 644 / chown`).
> 4. Проверяю, не занят ли порт другим процессом через `ss -tulpn`.

#### 23. КЕЙС: Сервер перестал отвечать на SSH и ping, в мониторинге горит красным. Что делать?
> **Ответ:**
> 1. Зайти в консоль гипервизора / облачную панель (VNC / Web-Console).
> 2. Проверить статус виртуальной машины (включена ли, загрузка CPU гипервизором).
> 3. Посмотреть экран консоли: нет ли **Kernel Panic**, зависания OOM или сбоя дискового контроллера.
> 4. Сделать скриншот экрана для отчета и отправить сервер в Hard Reboot.

#### 24. КЕЙС: Как безопасно очистить диск, если на сервере 100% full?
> **Ответ:**
> 1. Очистить логи systemd: `journalctl --vacuum-time=2d`.
> 2. Очистить неиспользуемый кэш контейнеров: `docker system prune -f`.
> 3. Найти тяжелые файлы `du -sh /* 2>/dev/null \| sort -hr`.
> 4. Если тяжелый лог открыт процессом — обнулить его через `truncate -s 0 /var/log/app.log` (**не через `rm`!**).

#### 25. КЕЙС: Что делать, если пришел алерт, но по нему нет готового Runbook?
> **Ответ:**
> 1. Провести первичную экспресс-диагностику (статус процессов, ресурсы CPU/RAM/Disk, последние логи ошибок).
> 2. Завести аварийный тикет в Jira и эскалировать инцидент на L2 / On-Call разработчика с прикреплением собранных логов.
> 3. После купирования аварии составить Post-Mortem и **написать недостающий Runbook в Confluence**, чтобы в следующий раз решить проблему по регламенту.
