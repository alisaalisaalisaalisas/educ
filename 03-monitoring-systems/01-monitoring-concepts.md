# 📈 Модуль 3.1: Концепции мониторинга: Метрики, Push vs Pull, SLA/SLO/SLI

Прежде чем настраивать дашборды и алерты, необходимо понимать фундаментальные принципы Observability (наблюдаемости).

---

## 1. Три столпа Observability (Наблюдаемости)

1. **Метрики (Metrics):** Числовые значения, агрегированные во времени (CPU %, количество RPS, свободная память). Легковесные, идеальны для графиков и триггеров алертов.
2. **Логи (Logs):** Текстовые записи о конкретных событиях во времени (`[2026-08-16 21:00] User login failed: wrong password`). Тяжелые, нужны для расследования причин (Root Cause Analysis).
3. **Трейсы (Traces):** Путь прохождения одного запроса через цепочку микросервисов (Frontend → API Gateway → Auth → DB). Показывают, на каком именно звене возникла задержка.

---

## 2. Модели сбора данных: Pull vs Push

### Pull-модель (Prometheus, VictoriaMetrics)
* Сервер мониторинга сам периодически опрашивает («скрейпит» / scrape) агентов и сервисы по HTTP (обычно эндпоинт `/metrics`).
* **Плюсы:** Сервер мониторинга контролирует нагрузку опроса; сразу видно, если хост недоступен (не отвечает на скрейп).
* **Минусы:** Сложнее мониторить динамические короткоживущие задачи (Batch jobs, лямбды) или сервисы за строгим NAT/Firewall.

### Push-модель (Zabbix Trapper, Graphite, StatsD)
* Агенты или сами приложения отправляют метрики на сервер мониторинга.
* **Плюсы:** Легко слать метрики из-за NAT; отлично подходит для коротких задач (запустился, отправил метрику, завершился).
* **Минусы:** Риск перегрузить сервер мониторинга потоком метрик (DDoS самого себя); труднее понять, сервис умер или у него просто нет трафика.

---

## 3. Метрики надежности: SLA, SLO, SLI

Эти термины часто спрашивают на собеседованиях:

* **SLI (Service Level Indicator):** Что конкретно мы измеряем?
  * *Пример:* Доля успешных ответов (HTTP 200) к общему числу запросов; 95-й процентиль времени ответа.
* **SLO (Service Level Objective):** Наша внутренняя цель для команды.
  * *Пример:* 99.9% запросов должны завершаться успешно.
* **SLA (Service Level Agreement):** Юридическое соглашение с клиентом и штрафы при нарушении.
  * *Пример:* Если доступность сервиса ниже 99.5% в месяц, компания возвращает деньги.
* **Error Budget (Бюджет ошибок):** Допустимое время простоя (`100% - SLO`). Для 99.9% доступности в месяц — это ~43 минуты простоя.

---

## 4. Золотые сигналы мониторинга (Google SRE Golden Signals)

Четыре главные вещи, которые нужно мониторить в любом веб-сервисе:
1. **Latency (Задержка):** Сколько времени занимает обработка запроса.
2. **Traffic (Трафик / Нагрузка):** Количество запросов в секунду (RPS).
3. **Errors (Ошибки):** Процент ошибочных ответов (5xx, 4xx).
4. **Saturation (Насыщение / Утилизация):** Насколько ресурс заполнен (память на 90%, переполнение пула коннектов к БД).
