# 📈 Модуль 3.1: Концепции мониторинга: Архитектура Observability, SRE-фреймворки и High Cardinality

Мониторинг — это базовый фундамент стабильности любой IT-инфраструктуры. Без качественной системы наблюдаемости невозможно оценить влияние релизов, предотвратить аварии и уложиться в соглашения об уровне сервиса (SLA).

---

## 🏛️ 1. Столпы Observability (Наблюдаемости)

Современная концепция **Observability** (в отличие от классического мониторинга «жив/мертв») позволяет ответить на вопрос: *«Почему система ведет себя не так, как ожидалось, внутри "черного ящика"?»*.

```text
                          ┌────────────────────────┐
                          │     OBSERVABILITY      │
                          └───────────┬────────────┘
         ┌──────────────────┬─────────┴──────────┬──────────────────┐
         ▼                  ▼                    ▼                  ▼
  ┌──────────────┐   ┌──────────────┐     ┌──────────────┐   ┌──────────────┐
  │   МЕТРИКИ    │   │     ЛОГИ     │     │    ТРЕЙСЫ    │   │  ПРОФАЙЛИНГ  │
  │  (Metrics)   │   │    (Logs)    │     │   (Traces)   │   │ (Profiling)  │
  ├──────────────┤   ├──────────────┤     ├──────────────┤   ├──────────────┤
  │ Агрегированные│  │ Детализация   │     │ Путь запроса │     Анализ строк │
  │ числа (CPU,  │   │ событий      │     │ через 10+    │   │ кода, жрущих │
  │ RAM, RPS).   │   │ с контекстом │     │ микросервисов│   │ CPU / Memory │
  │ Легковесные. │   │ и ошибками.  │     │ и задержки.  │   │ (Pyroscope). │
  └──────────────┘   └──────────────┘     └──────────────┘   └──────────────┘
```

1. **Метрики (Metrics):** Числовые значения с временными метками (`timestamp: value`) и метками (`labels`). Идеальны для графиков, расчетных дашбордов и триггеров алертов.
2. **Логи (Logs):** Структурированные текстовые записи о конкретных событиях (`timestamp`, `level`, `service`, `message`). Необходимы для расследования первопричин (Root Cause Analysis).
3. **Распределенные трейсы (Distributed Tracing):** Сквозное отслеживание цепочки вызовов между микросервисами с измерением времени каждого спана (Span).
4. **Непрерывный профайлинг (Continuous Profiling):** Анализ потребления CPU и аллокаций памяти прямо на уровне функций и строк исходного кода (Grafana Pyroscope, Parca).

## 🔄 2. Модели сбора данных: Pull vs Push

| Критерий | 📥 Pull-модель (Prometheus, VictoriaMetrics) | 📤 Push-модель (Zabbix Trapper, Graphite, OTel) |
| :--- | :--- | :--- |
| **Принцип** | Сервер мониторинга сам опрашивает (scrape) эндпоинты `/metrics` по HTTP. | Агенты или приложения сами отправляют данные на сервер мониторинга. |
| **Контроль нагрузки** | **Высокий**: сервер сам регулирует частоту опроса и не может быть «завален» входящим трафиком. | **Низкий**: при аварии тысячи подов могут устроить DDoS собственному мониторингу. |
| **Обнаружение падений** | **Мгновенное**: если сервер не получил ответ на скрейп, метрика `up == 0` сразу фиксирует аварию. | **Сложное**: трудно отличить умерший сервис от сервиса, у которого просто нет входящего трафика. |
| **Динамические и Batch задачи** | Требует промежуточный буфер (**Pushgateway**), так как cronjob может завершиться до скрейпа. | **Идеально**: скрипт выполнился, отправил метрику и завершился. |
| **Сети и Firewall/NAT** | Требует прямого сетевого доступа от сервера мониторинга к каждому хосту/поду. | Легко работает из-за строгого NAT/Firewall (агент стучится наружу). |

## 🧠 3. Внутреннее устройство TSDB (Базы данных временных рядов)

Prometheus использует специализированную TSDB, спроектированную под запись миллионов точек в секунду:

* **Временной ряд (Time Series):** Уникальная комбинация имени метрики и набора меток:
  `http_requests_total{method="POST", handler="/api/order", status="200"}`.
* **Сжатие данных (Chunking & Gorilla Algorithm):** Данные группируются в блоки по 2 часа. Метки времени и числа типа `float64` сжимаются алгоритмом дельта-дельта сжатия до **1-2 байт на точку**.
* **WAL (Write-Ahead Log):** Журнал упреждающей записи на диске. При аварийном ребуте сервера Prometheus восстанавливает несохраненные из оперативной памяти данные из WAL без потерь.
* **Compaction (Уплотнение):** Фоновый процесс объединения старых 2-часовых блоков в более крупные для ускорения выполнения запросов.

## 💣 4. Проблема высокой кардинальности (High Cardinality)

> **Cardinality (Кардинальность)** — это количество уникальных временных рядов в TSDB.
> Число рядов рассчитывается как **произведение количества уникальных значений всех лейблов**!

### 💥 Катастрофический пример

Разработчик добавил метку `user_id` и `ip_address` в метрику HTTP-запросов:

```promql
# ❌ СМЕРТЬ ДЛЯ PROMETHEUS:
http_requests_total{service="api", user_id="184920", client_ip="198.51.100.42", endpoint="/login"}
```

Если у вас 100 000 пользователей и 50 000 уникальных IP-адресов:
`1 (service) × 100 000 (пользователей) × 50 000 (IP) × 10 (эндпоинтов) = 50 000 000 000 рядов!`

* **Результат:** Prometheus моментально исчерпает всю RAM сервера (OOM Killer), база рухнет, восстановление займет часы.

### 🛡️ Золотые правила работы с лейблами

1. **Никогда не помещайте в лейблы метрик:** `user_id`, `email`, `order_id`, `uuid`, `jwt_token`, `client_ip`, `timestamp`.
2. **Используйте лейблы только с ограниченным набором значений (Low Cardinality):** `environment` (3 значения: prod, stage, dev), `status_code` (10 значений), `http_method` (5 значений: GET, POST...).
3. Если нужны уникальные ID пользователей — передавайте их **в логи (Loki / Elasticsearch) или трейсы (Tempo / Jaeger)**, но не в метрики!

## 📐 5. Три золотых фреймворка мониторинга

### 1. 🥇 Google 4 Golden Signals (Для распределенных приложений и API)

1. **Latency (Задержка):** Время обработки запроса. Важно различать задержку успешных ответов (`200 OK`) и ошибочных (`500 Error`), так как ошибки часто падают моментально и искажают среднее.
2. **Traffic (Трафик / Нагрузка):** Мера спроса на систему (RPS для HTTP API, транзакции в секунду TPS для БД).
3. **Errors (Ошибки):** Частота ошибочных запросов (явные HTTP 5xx, неявные ответы с пустым телом, таймауты).
4. **Saturation (Насыщение):** Заполненность самых узких ресурсов системы (память на 90%, переполнение пула потоков JVM, длина очереди диска).

---

### 2. 🚦 RED Method (Для микросервисов и сервисно-ориентированной архитектуры)

Предложен Томом Уилки (Tom Wilkie):

* **R — Rate:** Количество запросов в секунду (RPS).
* **E — Errors:** Количество запросов, завершившихся ошибкой в секунду.
* **D — Duration:** Время обработки запросов (гистограммы и процентили p95/p99).

---

### 3. ⚙️ USE Method (Для серверов, железа и сетевой инфраструктуры)

Предложен Бренданом Греггом (Brendan Gregg, Netflix):

* **U — Utilization (Утилизация):** Среднее время, в течение которого ресурс был занят полезной работой (CPU 80%, диск 60%).
* **S — Saturation (Насыщение / Очередь):** Объем дополнительной работы, которая не может быть обработана и встала в очередь (Load Average > CPU count, длина очереди сокетов `ListenBacklog`).
* **E — Errors (Ошибки):** Аппаратные и системные ошибки (битые пакеты на сетевом интерфейсе `rx_errors`, bad blocks на диске).

## 🎯 6. Культура SLA, SLO, SLI и Error Budget

```text
┌────────────────────────────────────────────────────────────────────────┐
│ SLA (Юридическое соглашение с клиентом и штрафы: Доступность ≥ 99.5%) │
│   ┌────────────────────────────────────────────────────────────────────┤
│   │ SLO (Внутренняя цель инженерной команды: Доступность ≥ 99.9%)       │
│   │   ┌────────────────────────────────────────────────────────────────┤
│   │   │ SLI (Точная математическая метрика: ratio успешных HTTP-запросов)│
└───┴───┴────────────────────────────────────────────────────────────────┘
```

### 🧮 Математика расчета

* **SLI (Индикатор):**
  $$\text{SLI} = \frac{\text{Количество успешных запросов (HTTP status < 500)}}{\text{Общее количество запросов}} \times 100\%$$

* **SLO (Целевой ориентир):** Устанавливается на основе SLI за скользящий период (например, за 30 дней) — $99.9\%$.

* **Error Budget (Бюджет ошибок):**
  $$\text{Error Budget} = 100\% - \text{SLO} = 100\% - 99.9\% = 0.1\%$$
  При 10 миллионах запросов в месяц команда имеет право «уронить» ровно $10\,000$ запросов без нарушения обязательств.

### ⏱️ Таблица допустимого простоя в зависимости от девяток

| Доступность (SLO) | Допустимый простой в ГОД | Допустимый простой в МЕСЯЦ |
| :--- | :--- | :--- |
| **99%** («Две девятки») | 3.65 дней | 7.3 часа |
| **99.9%** («Три девятки» — стандарт веб-сервисов) | 8.76 часов | **43.8 минуты** |
| **99.99%** («Четыре девятки» — FinTech, банки) | 52.6 минуты | **4.38 минуты** |
| **99.999%** («Пять девяток» — телеком/ядро) | 5.26 минут | **26 секунд** |

## 🔔 7. Культура Actionable Alerts (Борьба с Alert Fatigue)

> **Alert Fatigue (Усталость от алертов)** — болезнь дежурных инженеров, когда в Telegram сыплются сотни бесполезных сообщений, их перестают читать, и в итоге пропускается реальная катастрофа.

### 📜 Манифест правильного алерта

1. **Каждый алерт должен требовать конкретного действия человека (Actionable).** Если алерт не требует реакции прямо сейчас — это не алерт, а метрика на дашборде.
2. **Алертить по симптомам пользователей, а не по внутренним причинам.** Пользователю все равно, что CPU на ноде 95%, если сайт открывается мгновенно. Алерт должен срабатывать, когда растет Latency или летят ошибки 5xx.
3. **Обязательное наличие ссылки на Runbook (Инструкцию по устранению).** Дежурный инженер ночью не должен гадать, что делать при получении алерта.
4. **Защита от дребезга (Flapping):** Использовать интервал `for: 5m`, чтобы не спамить при секундных пиках нагрузки.

## 🚫 8. Таблица антипаттернов в мониторинге

| ❌ Антипаттерн | В чем опасность | ✅ Как делать правильно |
| :--- | :--- | :--- |
| Добавление динамических данных в метки (`user_id`, `ip`) | Взрывной рост кардинальности (High Cardinality) ➔ OOM TSDB. | Использовать статичные метки, а детали передавать в логи и трейсы. |
| Алерт на каждое колебание CPU > 80% без параметра `for:` | Ложные срабатывания при кратковременных задачах (Alert Fatigue). | Ставить `for: 5m` или `10m` и алертить по симптомам (Errors/Latency). |
| Мониторинг средней задержки (`avg latency`) | Среднее скрывает страдания 5% пользователей (например, 95% запросов идут 10мс, а 5% ждут 10 секунд). | Использовать процентили: p95, p99 (`histogram_quantile`). |
| Отсутствие дедупликации и группировки | При падении коммутатора дежурный получает 500 алертов вместо одного. | Настраивать группировку (`group_by`) и ингибирование (`inhibit_rules`). |
| Дашборд из 100 графиков без структуры | Во время инцидента невозможно найти нужный график за 30 секунд. | Использовать 3-уровневую структуру дашбордов (Overview ➔ Service ➔ Debug). |
