# 📖 Модуль 6.2: Runbooks: Решение типовых аварий

**Runbook (Инструкция / Плейбук)** — пошаговый алгоритм действий дежурного при срабатывании конкретного алерта.

---

## 🛠️ Runbook 1: Алерт «502 Bad Gateway / High 5xx Error Rate»

### Что это значит:
Nginx не может получить ответ от апстрима (Node.js / Python Gunicorn / PHP-FPM / Java). Бэкенд либо упал, либо завис, либо перегружен.

### Пошаговый алгоритм действий:
1. **Проверить логи Nginx:**
   ```bash
   tail -n 50 /var/log/nginx/error.log
   ```
   * Если видно `connect() failed (111: Connection refused)` → бэкенд выключен или упал.
   * Если видно `no live upstreams while connecting to upstream` → все реплики бэкенда недоступны.
2. **Проверить статус процессов бэкенда:**
   ```bash
   systemctl status backend-app
   # или для Docker:
   docker ps -a | grep backend
   ```
3. **Проверить OOM Killer:**
   ```bash
   dmesg -T | grep -i "oom" | tail -n 10
   ```
   * Если бэкенд убит по памяти, зафиксировать инцидент, перезапустить службу (`systemctl restart backend-app` или `docker restart backend`), сообщить разработчикам об утечке памяти (Memory Leak).
4. **Проверить доступность локального порта бэкенда:**
   ```bash
   curl -I http://127.0.0.1:8080/health
   ```

## 🛠️ Runbook 2: Алерт «Disk Space < 10% (Root Partition Full)»

### Что это значит:
Диск забился логами, временными файлами или дампами баз данных. При 100% заполнении перестанут запускаться сервисы и писать логи.

### Пошаговый алгоритм действий:
1. **Найти точку монтирования:**
   ```bash
   df -h
   ```
2. **Найти самую тяжелую директорию:**
   ```bash
   du -sh /var/* 2>/dev/null | sort -hr | head -n 5
   du -sh /var/log/* 2>/dev/null | sort -hr | head -n 5
   ```
3. **Безопасная очистка (НЕ удалять файлы вслепую!):**
   * **Очистка старых системных логов:**
     ```bash
     journalctl --vacuum-time=2d  # Оставить логи только за последние 2 дня
     ```
   * **Очистка Docker кэша:**
     ```bash
     docker system prune -f
     ```
   * **Если лог-файл открыт процессом (удаление через `rm` не освободит место):**
     ```bash
     # Правильное обнуление лога без удаления дескриптора:
     truncate -s 0 /var/log/heavy_app.log
     ```
4. **Проверить удаленные, но удерживаемые процессами файлы:**
   ```bash
   lsof | grep deleted
   ```

## 🛠️ Runbook 3: Алерт «High CPU Load (Load Average > 20)»

### Пошаговый алгоритм действий:
1. **Открыть `top` или `htop`:**
   * Посмотреть `%usr` (пользовательские вычисления), `%sys` (ядро) и `%wa` (ожидание диска).
2. **Если высокий `%wa` (iowait):**
   * Проблема не в процессоре, а в медленном диске (кто-то пишет огромный бэкап или база делает full scan).
   * Запустить `iotop -o` для выявления процесса-виновника.
3. **Если один процесс грузит CPU на 100%:**
   ```bash
   ps aux --sort=-%cpu | head -n 5
   ```
   * Если это зависший воркер — сделать thread dump (для разработчиков) и аккуратно перезапустить процесс (`kill -15 <PID>`, если не отвечает — `kill -9 <PID>`).
