# ☸️ Модуль 5.3: Kubernetes: Базовый Траблшутинг (Read-Only для Дежурного)

Для работы в мониторинге и дежурствах **не нужно** уметь разворачивать кластер или писать сложные Helm-чарты. Главная задача — **быстро найти сломанный под, понять причину падения и эскалировать проблему**.

---

## 1. Базовые концепции K8s простыми словами

* **Cluster (Кластер):** Группа серверов (Master Nodes — управляющие, Worker Nodes — рабочие).
* **Namespace (Пространство имен):** Изоляция окружений (например, `production`, `staging`, `monitoring`).
* **Pod (Под):** Минимальная единица развертывания (один или несколько связанных контейнеров).
* **Deployment:** Контроллер, управляющий количеством реплик подов и их обновлениями.
* **Service:** Внутренний балансировщик нагрузки и стабильный DNS-адрес для доступа к группе подов.

---

## 2. Шпаргалка по командам `kubectl` (Must-Have)

```bash
# 1. Посмотреть поды во всех неймспейсах
kubectl get pods -A
kubectl get pods -n production

# 2. Вывести список подов с расширенной информацией (IP, нода, рестарты)
kubectl get pods -o wide -n production

# 3. Посмотреть подробное состояние и события (Events) пода
kubectl describe pod <pod_name> -n production

# 4. Просмотр логов пода в реальном времени
kubectl logs -f <pod_name> -n production
kubectl logs -f <pod_name> -c <container_name> -n production # если в поде несколько контейнеров
kubectl logs --previous <pod_name> -n production            # Логи ПРЕДЫДУЩЕГО (упавшего) запуска

# 5. Просмотр потребления ресурсов нодами и подами (требует Metrics Server)
kubectl top nodes
kubectl top pods -n production --sort-by=memory
```

## 3. Расшифровка аварийных статусов подов (Топ на собеседованиях)

### 🔴 1. `CrashLoopBackOff`
* **Что значит:** Приложение внутри контейнера запустилось, упало с ошибкой, Kubernetes пытается перезапустить его снова и снова с увеличивающейся задержкой.
* **Как лечить:**
  ```bash
  # Смотрим логи упавшего контейнера:
  kubectl logs <pod_name> -n <namespace> --previous
  ```
* **Частые причины:** Ошибка конфигурации (нет переменной окружения), ошибка подключения к базе данных, синтаксический exception в коде.

---

### 🔴 2. `OOMKilled` (Exit Code 137)
* **Что значит:** Контейнер потребил больше оперативной памяти, чем указано в `resources.limits.memory`, и был принудительно убит ядром.
* **Как обнаружить:**
  ```bash
  kubectl describe pod <pod_name> -n <namespace> | grep -i oom
  # В выводе будет: Last State: Terminated, Reason: OOMKilled, Exit Code: 137
  ```
* **Решение:** Эскалировать разработчикам (утечка памяти) или DevOps для увеличения лимита памяти.

---

### 🔴 3. `ImagePullBackOff` / `ErrImagePull`
* **Что значит:** Kubernetes не смог скачать Docker-образ с реестра (Registry / Docker Hub / GitLab Registry).
* **Частые причины:** Опечатка в теге образа, не настроен `imagePullSecrets` (нет прав на приватный реестр), реестр образов недоступен.

---

### 🔴 4. `Pending`
* **Что значит:** Под создан, но планировщик (Scheduler) не может назначить его ни на одну ноду.
* **Частые причины:** В кластере закончились ресурсы CPU/Memory (некуда разместить под), ноды помечены Taints (запрет размещения). Смотреть `kubectl describe pod`.

---

### 🔴 5. `Node NotReady`
* **Что значит:** Вся физическая/виртуальная нода кластера перестала отвечать мастеру.
* **Частые причины:** Упал сервис `kubelet`, пропала сеть до ноды, диск забился на 100% (DiskPressure).
