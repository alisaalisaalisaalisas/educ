# 🐳 Модуль 5.1: Docker: Архитектура, команды и культура написания Dockerfile

Контейнеризация — это фундаментальный стандарт современной доставки приложений. Docker упаковывает приложение, его зависимости, конфигурации и системные библиотеки в легковесный изолированный образ, гарантируя одинаковую работу в окружениях `local ➔ dev ➔ staging ➔ production`.

---

## 🏗️ 1. Архитектура: Контейнер vs Виртуальная машина

```
    ┌───────────────────────────────┐        ┌───────────────────────────────┐
    │       ВИРТУАЛЬНАЯ МАШИНА      │        │        DOCKER КОНТЕЙНЕР       │
    ├───────────────────────────────┤        ├───────────────────────────────┤
    │  App A   │  App B   │  App C  │        │  App A   │  App B   │  App C  │
    ├──────────┼──────────┼─────────┤        ├──────────┼──────────┼─────────┤
    │ Bins/Libs│ Bins/Libs│Bins/Libs│        │ Bins/Libs│ Bins/Libs│Bins/Libs│
    ├──────────┼──────────┼─────────┤        ├───────────────────────────────┤
    │ Guest OS │ Guest OS │ Guest OS│        │       Docker Engine (runc)    │
    ├───────────────────────────────┤        ├───────────────────────────────┤
    │      Гипервизор (KVM, ESXi)   │        │     Единое ядро Linux Host    │
    ├───────────────────────────────┤        ├───────────────────────────────┤
    │    Железо сервера (Bare Metal)│        │    Железо сервера (Bare Metal)│
    └───────────────────────────────┘        └───────────────────────────────┘
```

### Механизмы изоляции в ядре Linux:
1. **Namespaces (Пространства имен):** Изолируют видимость системных ресурсов для процесса:
   * `pid` — изолированное дерево процессов (контейнер видит себя как PID 1).
   * `net` — изолированные сетевые интерфейсы, IP-адреса, порты и таблицы маршрутизации.
   * `mnt` — изолированная файловая система (своя корневая FS).
   * `ipc` — изолированная межпроцессная память и очереди сообщений.
   * `uts` — изолированное имя хоста (hostname).
   * `user` — маппинг UID/GID пользователей хоста в контейнер.
2. **Cgroups (Control Groups):** Ограничивают потребление физических ресурсов: лимиты CPU, памяти (RAM), ввода-вывода (Disk I/O) и числа процессов (`pids.max`).
3. **OverlayFS (Union File System):** Слоистая файловая система, объединяющая слои образа (Read-Only) и слой контейнера (Read-Write) через механизм Copy-on-Write (CoW).

## 📋 2. Шпаргалка по командам Docker для инженера

```bash
# -------------------------------------------------------------
# 1. Управление контейнерами
# -------------------------------------------------------------
docker ps                              # Список только запущенных контейнеров
docker ps -a                           # Список ВСЕХ контейнеров (включая остановленные/упавшие)
docker ps -q                           # Вывести только ID контейнеров
docker run -d --name app -p 8080:80 nginx:alpine # Фоновый запуск с пробросом портов

# -------------------------------------------------------------
# 2. Диагностика и инспекция
# -------------------------------------------------------------
docker logs -f --tail 100 <container>  # Логи в реальном времени (последние 100 строк)
docker logs --since 10m <container>    # Логи за последние 10 минут
docker logs -t <container>             # Вывод логов с точными timestamp
docker stats --no-stream               # Мониторинг CPU, RAM, Network I/O в реальном времени
docker top <container>                 # Список процессов, запущенных внутри контейнера

# Инспекция JSON-конфигурации:
docker inspect <container>             # Полная информация (IP, монтирования, ENV, состояние)
# Быстро получить IP контейнера через jsonpath/Go-шаблон:
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' <container>
# Проверить статус Healthcheck:
docker inspect -f '{{json .State.Health.Status}}' <container>

# -------------------------------------------------------------
# 3. Интерактивная работа и отладка
# -------------------------------------------------------------
docker exec -it <container> /bin/bash  # Зайти внутрь работающего контейнера в bash
docker exec -it <container> /bin/sh    # Для Alpine и минималистичных образов (где нет bash)
docker exec -u 0 -it <container> sh    # Зайти от имени root (для экстренной отладки)
docker cp ./config.json <container>:/etc/app/config.json # Скопировать файл в контейнер

# -------------------------------------------------------------
# 4. Очистка и освобождение диска (Garbage Collection)
# -------------------------------------------------------------
docker system df                       # Анализ занимаемого места на диске Docker-объектами
docker system prune -a --volumes -f    # Удалить ВСЕ неиспользуемые контейнеры, сети, образы и тома
docker image prune -a                  # Удалить все неиспользуемые образы
docker volume prune                    # Удалить все «висячие» (dangling) тома
```

## 🎨 3. Культура правильного написания `Dockerfile` (Best Practices)

Написание `Dockerfile` — это инженерное искусство баланса между **скоростью сборки**, **размером итогового образа**, **безопасностью** и **надежностью рантайма**.

### 🧱 Анатомия инструкций Dockerfile:
| Инструкция | Назначение | Правило культуры |
| :--- | :--- | :--- |
| `FROM` | Базовый образ | Всегда указывать точную версию (`node:20.11-alpine3.19`), избегать `:latest`. |
| `WORKDIR` | Рабочая директория | Всегда использовать абсолютные пути (`WORKDIR /app`), не использовать `RUN mkdir && cd`. |
| `COPY` vs `ADD` | Копирование файлов | Всегда использовать `COPY`. `ADD` нужен **только** для автоматической распаковки `.tar.gz`. |
| `RUN` | Выполнение команд сборки | Объединять связанные команды через `&&` и очищать кэш пакетов в том же слое. |
| `USER` | Пользователь процесса | **Никогда не запускать от root в продакшене!** Создавать и переключаться на `appuser`. |
| `EXPOSE` | Документирование порта | Носит информационный характер, порт реально не открывается наружу без `-p`. |
| `ENV` vs `ARG` | Переменные | `ARG` доступен только во время `docker build`, `ENV` сохраняется в рантайме контейнера. |
| `ENTRYPOINT` vs `CMD` | Команда запуска | Использовать Exec-форму (JSON массив: `["node", "server.js"]`), а не Shell-форму. |

---

### 🚀 Золотые правила культуры Dockerfile:

#### 1. Эффективное кэширование слоев (Layer Caching)
Docker кэширует каждый слой `Dockerfile`. Если слой изменился, все последующие слои пересобираются заново.
* ❌ **Плохо (кэш сбрасывается при любом изменении 1 строчки кода):**
  ```dockerfile
  COPY . .
  RUN npm install  # Выполняется заново при каждом коммите!
  ```
* ✅ **Идеально (кэш зависимостей сохраняется):**
  ```dockerfile
  # Сначала копируем только манифесты зависимостей
  COPY package.json package-lock.json ./
  RUN npm ci --only=production
  # И только затем исходный код, который меняется часто
  COPY src/ ./src/
  ```

#### 2. Многоэтапная сборка (Multi-stage Builds)
В финальном образе **не должно быть компиляторов, SDK, заголовков C++ и dev-зависимостей**.

```dockerfile
# ==========================================
# Этап 1: Сборка приложения (Build Stage)
# ==========================================
FROM node:20-alpine AS builder

WORKDIR /build

# Установка зависимостей сборки
COPY package.json package-lock.json ./
RUN npm ci

# Сборка TypeScript / React / Next.js
COPY . .
RUN npm run build && npm prune --production

# ==========================================
# Этап 2: Финальный минимальный рантайм (Production Stage)
# ==========================================
FROM node:20-alpine AS runner

# Настройка переменных окружения
ENV NODE_ENV=production \
    PORT=3000

WORKDIR /app

# Создание непривилегированного системного пользователя
RUN addgroup -g 10001 -S appgroup && \
    adduser -u 10001 -S appuser -G appgroup

# Копируем из builder ТОЛЬКО скомпилированные артефакты и продакшн-модули
COPY --from=builder --chown=appuser:appgroup /build/dist ./dist
COPY --from=builder --chown=appuser:appgroup /build/node_modules ./node_modules
COPY --from=builder --chown=appuser:appgroup /build/package.json ./package.json

# Переключаемся на безопасного пользователя
USER appuser

EXPOSE 3000

# Запуск в exec-форме
CMD ["node", "dist/main.js"]
```

#### 3. Безопасность: Non-root User и Privileges
* Если злоумышленник взломает приложение, работающее от `root` в контейнере, уязвимость в ядре позволит ему получить **root-доступ ко всему физическому хосту (Container Escape)**.
* Всегда объявляйте непривилегированного пользователя:
  ```dockerfile
  RUN groupadd -r appgroup -g 1001 && useradd -r -u 1001 -g appgroup -s /sbin/nologin appuser
  USER appuser
  ```

#### 4. Правильная обработка сигналов и PID 1 (`tini` / `dumb-init`)
* Процесс с PID 1 в Linux отвечает за усыновление зомби-процессов и получение сигналов ОС (`SIGTERM`, `SIGINT`).
* Node.js, Python, Java исторически **не умеют работать в роли PID 1** и игнорируют `SIGTERM`. Из-за этого при `docker stop` контейнер «висит» 10 секунд и убивается жестким `SIGKILL` (`kill -9`), теряя данные и обрывая транзакции клиентов.
* **Решение:** Использовать легковесный `tini` или `dumb-init`:
  ```dockerfile
  # Установка tini в Alpine
  RUN apk add --no-cache tini
  ENTRYPOINT ["/sbin/tini", "--"]
  CMD ["node", "server.js"]
  ```

#### 5. Использование `.dockerignore`
Всегда создавайте `.dockerignore` рядом с `Dockerfile`, чтобы не передавать в демон Docker гигабайты мусора и секреты:
```gitignore
.git
.gitignore
node_modules
dist
build
.env
.env.*
*.log
Dockerfile*
docker-compose*.yml
.DS_Store
coverage/
```

#### 6. Выбор базового образа: сравнение
| Образ | Плюсы | Минусы | Когда применять |
| :--- | :--- | :--- | :--- |
| **Debian Slim** (`python:3.12-slim`) | Стабильный glibc, совместим со всеми C-библиотеками | Размер ~100-150 МБ | Python (numpy/pandas), C-extensions |
| **Alpine Linux** (`alpine:3.19`) | Микроскопический размер (~5-10 МБ), быстрый pull | Использует `musl libc` (бывают баги с C/C++ биндингами) | Go, Node.js, статичные утилиты |
| **Google Distroless** (`gcr.io/distroless/static`) | Нет package manager и shell (`/bin/sh`). 0 лишних CVE! | Сложно дебажить внутри контейнера | Enterprise Production (Go, Java, Rust) |
| **Scratch** | Пустой слой (0 байт) | Только статически скомпилированные бинарники | Go, Rust (полный standalone binary) |

## 🔍 4. Линтинг и сканирование уязвимостей в CI/CD

В культуре DevOps сборка не должна попадать в репозиторий без автоматических проверок:

### 1. `Hadolint` (Линтер Dockerfile)
Проверяет код `Dockerfile` на соответствие лучшим практикам:
```bash
# Локальная проверка через Docker
docker run --rm -i hadolint/hadolint < Dockerfile
```
* `DL3008`: Всегда фиксируйте версии пакетов в `apt-get install <pkg>=<version>`.
* `DL3009`: Удаляйте кэш менеджера пакетов (`rm -rf /var/lib/apt/lists/*`).
* `DL3020`: Используйте `COPY` вместо `ADD`.
* `DL3002`: Последний пользователь не должен быть `root`.

### 2. `Trivy` (Сканер уязвимостей CVE)
```bash
# Сканирование образа на известные уязвимости (CVE)
trivy image --severity HIGH,CRITICAL my-app:1.0.0
```

## 🚫 5. Таблица антипаттернов в Docker

| ❌ Антипаттерн | Почему это плохо | ✅ Как делать правильно |
| :--- | :--- | :--- |
| Использование тега `:latest` | Неповторяемые сборки: образ сломается при выходе мажорной версии зависимости. | Пинговать конкретные теги: `postgres:16.2-alpine3.19`. |
| Хранение паролей и токенов в `ENV` внутри Dockerfile | Секреты навсегда останутся видны в истории слоев `docker history`. | Передавать секреты в рантайме через K8s Secrets, Vault или Docker Secrets. |
| Множество мелких `RUN apt-get` | Создается много слоев, размер образа раздувается до гигабайтов. | Объединять команды через `&&` в один слой и чистить кэш в конце. |
| Запуск от `root` (`UID 0`) | Риск выхода из контейнера на хост (Container Escape). | Создавать отдельного пользователя `USER 10001`. |
| Shell-форма для CMD: `CMD node app.js` | Запускается `/bin/sh -c`, который не передает сигнал `SIGTERM` процессу Node.js. | Exec-форма: `CMD ["node", "app.js"]`. |
| Запись логов в файл внутри контейнера | Логи теряются при удалении контейнера, раздувают RW-слой. | Писать логи только в `stdout` / `stderr`. |
