# 🔍 Модуль 4.2: Стек ELK / OpenSearch: Filebeat, Logstash, ILM, Elastic Common Schema (ECS) и KQL

Стек **ELK (Elasticsearch, Logstash, Kibana)** и его открытый форк **OpenSearch (OpenSearch, Fluentbit/Filebeat, OpenSearch Dashboards)** — классический отраслевой стандарт централизованного логирования с мощным полнотекстовым поиском по любым полям.

---

## 🏛️ 1. Архитектура распределенного кластера

```text
 ┌───────────────────────┐   ┌───────────────────────┐
 │   Filebeat (Host 1)   │   │   Filebeat (Host 2)   │
 └───────────┬───────────┘   └───────────┬───────────┘
             │ (Port 5044 / Lumberjack)  │
             └─────────────┬─────────────┘
                           ▼
             ┌───────────────────────────┐
             │         LOGSTASH          │
             │ (Grok, Mutate, Date, Geo) │
             └─────────────┬─────────────┘
                           │ (Bulk HTTP API)
                           ▼
┌─────────────────────────────────────────────────────────────┐
│               ELASTICSEARCH / OPENSEARCH CLUSTER            │
│                                                             │
│  ┌───────────────────────┐     ┌─────────────────────────┐  │
│  │ Master-Eligible Node  │     │ Ingest / Pipeline Node  │  │
│  │ (Управление кластером)│     │ (Парсинг JSON/GeoIP)    │  │
│  └───────────────────────┘     └─────────────────────────┘  │
│                                                             │
│  ┌───────────────────────────────────────────────────────┐  │
│  │ Data Nodes (Hot / Warm / Cold Tier)                   │  │
│  │ ┌───────────────────────┐   ┌───────────────────────┐ │  │
│  │ │ Primary Shard (P0)    │   │ Replica Shard (R0)    │ │  │
│  │ └───────────────────────┘   └───────────────────────┘ │  │
│  └───────────────────────────────────────────────────────┘  │
└──────────────────────────────┬──────────────────────────────┘
                               │
                               ▼
                 ┌───────────────────────────┐
                 │  KIBANA / OPENSEARCH UI   │
                 │ (Discover, Visualize, KQL)│
                 └───────────────────────────┘
```

### Роли нод в кластере:

* **`master`**: Управляет метаданными кластера, создает и переносит шарды между серверами.
* **`data_hot`**: Записывает свежие входящие логи (требует быстрых NVMe SSD и много RAM для кэша).
* **`data_warm / data_cold`**: Хранит старые архивные логи (только для чтения, медленные HDD или S3).
* **`ingest`**: Выполняет предобработку документов перед индексацией без участия Logstash.
* **`coordinating`**: Принимает тяжелые поисковые запросы от Kibana, распределяет их по нодам и склеивает результат.

## 📜 2. Культура написания конфигурации Filebeat (`filebeat.yml`)

Ниже представлен эталонный манифест агента сбора логов со склейкой многострочных стектрейсов (Multiline) и фильтрацией мусора:

```yaml
filebeat.inputs:
  # -------------------------------------------------------------
  # 1. Сбор логов Docker / Kubernetes контейнеров
  # -------------------------------------------------------------
  - type: container
    paths:
      - '/var/log/pods/*/*/*.log'
    # Склейка многострочных Java / Python Stack Traces:
    multiline.type: pattern
    # Строка считается новой, если начинается с даты YYYY-MM-DD:
    multiline.pattern: '^[0-9]{4}-[0-9]{2}-[0-9]{2}'
    multiline.negate: true
    multiline.match: after
    multiline.max_lines: 500
    multiline.timeout: 5s

# =============================================================
# Процессоры обогащения и фильтрации (Processors)
# =============================================================
processors:
  # 1. Добавляем метаданные Docker (имя контейнера, образ, лейблы)
  - add_docker_metadata:
      host: "unix:///var/run/docker.sock"

  # 2. Добавляем метаданные хоста (hostname, архитектура, IP)
  - add_host_metadata:
      netinfo.enabled: true

  # 3. Отсекаем шумные проверки здоровья (healthcheck / probe)
  - drop_event:
      when:
        or:
          - regexp:
              message: ".*(healthz|readyz|kube-probe).*"
          - equals:
              http.response.status_code: 200

# =============================================================
# Отправка данных в Logstash
# =============================================================
output.logstash:
  hosts: ["logstash-01.internal:5044", "logstash-02.internal:5044"]
  loadbalance: true
  worker: 2
  compression_level: 3
```

## ⚙️ 3. Пайплайн обработки данных Logstash (`logstash.conf`)

Пайплайн Logstash состоит из 3 блоков: `input`, `filter` и `output`:

```ruby
# =============================================================
# 1. Входной поток (Input)
# =============================================================
input {
  beats {
    port => 5044
    ssl  => false
  }
}

# =============================================================
# 2. Фильтрация, парсинг и трансформация (Filter)
# =============================================================
filter {
  # Если лог уже в формате JSON — автоматически распаковать поля
  if [message] =~ /^\{.*\}$/ {
    json {
      source => "message"
    }
  } else {
    # Для классических логов Nginx применяем паттерн Grok
    grok {
      match => { "message" => "%{COMBINEDAPACHELOG}" }
      tag_on_failure => ["_grokparsefailure"]
    }
  }

  # Синхронизация временной метки документа с реальным временем события
  date {
    match => [ "timestamp", "ISO8601", "dd/MMM/yyyy:HH:mm:ss Z" ]
    target => "@timestamp"
    remove_field => [ "timestamp" ]
  }

  # Обогащение по IP-адресу (Геолокация клиента: Страна, Город)
  if [client_ip] {
    geoip {
      source => "client_ip"
      target => "geoip"
    }
  }

  # Удаление лишних служебных полей для экономии диска
  mutate {
    remove_field => [ "agent", "ecs", "input", "tags" ]
  }
}

# =============================================================
# 3. Выходной поток (Output в Elasticsearch)
# =============================================================
output {
  elasticsearch {
    hosts => ["http://es-master-01:9200", "http://es-master-02:9200"]
    # Именование индексов по дням с привязкой к сервису:
    index => "logs-%{[service][name]}-%{+YYYY.MM.dd}"
    user  => "logstash_internal"
    password => "${LOGSTASH_PASSWORD}"
  }
}
```

## 🗄️ 4. Управление жизненным циклом индексов (ILM / ISM)

> 💡 Чтобы диск не забился терабайтами старых логов, настраивают **Index Lifecycle Management (ILM)**.

```text
┌────────────────────────────────────────────────────────────────────────┐
│                        ЖИЗНЕННЫЙ ЦИКЛ ИНДЕКСА                          │
├────────────────────────────────────────────────────────────────────────┤
│ 1. HOT ФАЗА (1–7 дней):                                                │
│    Индекс открыт на запись (Write). Работает на быстрых NVMe SSD.      │
├────────────────────────────────────────────────────────────────────────┤
│ 2. WARM ФАЗА (8–30 дней):                                              │
│    Запись закрыта (Read-Only). Выполняется сжатие сегментов            │
│    (Force Merge) и перенос на более дешевые SATA SSD.                  │
├────────────────────────────────────────────────────────────────────────┤
│ 3. COLD ФАЗА (31–90 дней):                                             │
│    Индекс заморожен (Searchable Snapshot в S3/MinIO), без реплик.      │
├────────────────────────────────────────────────────────────────────────┤
│ 4. DELETE ФАЗА (> 90 дней):                                            │
│    Индекс полностью и безвозвратно удаляется из кластера.              │
└────────────────────────────────────────────────────────────────────────┘
```

## 🏷️ 5. Стандарт Elastic Common Schema (ECS)

В культуре логирования недопустимо, чтобы в одном сервисе статус ответа назывался `http_code`, во втором `status`, а в третьем `statusCode`.
Для этого используется стандарт **ECS (Elastic Common Schema)**:

| Поле ECS | Тип | Описание | Пример значения |
| :--- | :--- | :--- | :--- |
| `@timestamp` | `date` | Точное время события в UTC ISO8601 | `2026-08-16T21:00:15.123Z` |
| `log.level` | `keyword` | Уровень логирования | `ERROR`, `WARN`, `INFO` |
| `service.name` | `keyword` | Имя микросервиса | `billing-api` |
| `service.version` | `keyword` | Версия релиза | `1.4.2` |
| `trace.id` | `keyword` | Сквозной ID распределенного трейса | `4bf92f3577b34da6a3ce929d0e0e4736` |
| `http.response.status_code`| `long` | Код ответа веб-сервера | `504` |
| `error.message` | `text` | Текст ошибки / Exception | `Connection to DB timed out` |
| `error.stack_trace` | `text` | Полный стектрейс ошибки | `NullPointerException at main.go:42` |

## 🔎 6. Поиск в Kibana: KQL и Lucene Syntax

### Язык KQL (Kibana Query Language)

```kql
# 1. Поиск точного совпадения по сервису и уровню
service.name: "orders-api" and log.level: "ERROR"

# 2. Поиск диапазона кодов ответа (все 5xx ошибки)
http.response.status_code >= 500 and http.response.status_code <= 599

# 3. Поиск по вхождению подстроки (Wildcard)
message: *ConnectionRefused*

# 4. Проверка существования поля (найти все записи со стектрейсом)
error.stack_trace: *

# 5. Исключение мусорных логов
not (service.name: "cron" and log.level: "DEBUG")
```

## 🆚 7. Сравнительная матрица: Loki vs ELK / OpenSearch

| Критерий | 🪵 Grafana Loki | 🔍 ELK / OpenSearch |
| :--- | :--- | :--- |
| **Индексация** | Индексирует **только лейблы** (легковесный TSDB-индекс). | Индексирует **весь текст** каждого документа (Apache Lucene). |
| **Потребление RAM / CPU** | **Экстремально низкое** (в 4–5 раз меньше ELK). | **Высокое** (JVM требует от 32 ГБ RAM на ноду). |
| **Стоимость диска / S3** | **Минимальная** (сжатые чанки прямо в S3, 1–2 байта/символ). | **Высокая** (индексы Lucene занимают до 120–150% размера сырых логов). |
| **Скорость точечного поиска** | Медленнее при поиске по 10 ТБ за год (сканирует чанки). | **Мгновенная** (секунды даже на петабайтах данных). |
| **Сложность эксплуатации** | Простая (один бинарник + S3 бакет). | Высокая (тюнинг шардов, реплик, JVM Heap, GC, Split-Brain). |

## 🚫 8. Таблица антипаттернов в ELK/OpenSearch

| ❌ Антипаттерн | Почему это плохо | ✅ Как делать правильно |
| :--- | :--- | :--- |
| Выделение JVM Heap более 31 ГБ (`-Xmx32g`) | Отключается оптимизация Compressed OOPs (указателей), расход памяти возрастает в 1.5 раза. | Задавать `Xms` и `Xmx` **не более 31 ГБ** (ровно 50% RAM сервера). |
| Создание 1000 мелких шардов по 50 МБ | Перегрузка памяти Master-ноды, резкое падение скорости поиска. | Держать размер одного шарда в диапазоне **20–50 ГБ**. |
| Отсутствие политик ILM (ротации) | Индексы забивают диск на 100%, кластер переходит в статус `ClusterBlockException` (Read-Only). | Настраивать ILM с ротацией в Warm/Cold и удалением через 30–90 дней. |
| Неструктурированные логи без ECS | Поиск `status` не находит логи, где разработчик написал `http_code`. | Внедрять единый стандарт **Elastic Common Schema (ECS)**. |
