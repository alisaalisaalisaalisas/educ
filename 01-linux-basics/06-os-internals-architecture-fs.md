# 🏗️ Модуль 1.6: Внутреннее устройство ОС: Архитектуры (x86_64 vs ARM), Процессы и Файловые системы

Этот модуль закрывает все фундаментальные вопросы об устройстве операционной системы и «железа», которые любят задавать на технических собеседованиях.

---

## 1. Архитектуры процессоров: x86, x86_64 (AMD64) и ARM64 (aarch64)

Архитектура процессора определяет набор инструкций (машинный код), который процессор умеет выполнять.

| Архитектура | Другие названия | Где используется | Особенности для Ops / DevOps |
| :--- | :--- | :--- | :--- |
| **x86** | i386, 32-bit | Устаревшее железо | Адресует максимум **4 ГБ оперативной памяти**. Сейчас практически не используется на серверах. |
| **x86_64** | **AMD64**, x64, Intel 64 | 85%+ серверов в ЦОД (Intel Xeon, AMD EPYC) | 64-битная адресация памяти (терабайты RAM). Стандарт для большинства корпоративных серверов. |
| **ARM64** | **aarch64**, ARMv8/v9 | Apple Silicon (M1/M2/M3), AWS Graviton, смартфоны, Raspberry Pi | Энергоэффективные процессоры с RISC-архитектурой. Дешевле в облаках (AWS Graviton стоит на 20% дешевле x86). |

### ⚠️ Главная боль инженера: «Exec format error» в Docker
Если разработчик собрал Docker-образ на своем MacBook (чип ARM64) и отправил его на продакшен-сервер (Intel x86_64), сервер не сможет выполнить инструкции и упадет с ошибкой:
```
standard_init_linux.go: exec user process caused: exec format error
```
* **Решение:** Сборка мультиплатформенных образов через `docker buildx build --platform linux/amd64,linux/arm64`.

## 2. Иерархия файловой системы Linux (FHS - Filesystem Hierarchy Standard)

В Linux нет дисков `C:`, `D:`. Есть единое дерево каталогов, начинающееся с корня `/`:

```
/
├── bin / sbin     -> Исполняемые бинарники (ls, grep, systemctl, ping)
├── etc/           -> Конфигурационные файлы всех сервисов (nginx, sshd, hosts, resolv.conf)
├── var/           -> Изменяемые данные: логи (/var/log), базы данных (/var/lib), кэш
├── tmp/           -> Временные файлы (очищаются при перезагрузке)
├── opt/           -> Стороннее ПО (например, /opt/alloy, /opt/gitlab)
├── home/          -> Домашние директории обычных пользователей (/home/user)
├── root/          -> Домашняя директория суперпользователя root
├── dev/           -> Файлы устройств (/dev/sda - диск, /dev/null - «черная дыра», /dev/random)
├── proc/          -> Виртуальная ФС: информация о ядре и процессах в RAM
└── sys/           -> Виртуальная ФС: информация о железе, шинах и драйверах
```

## 3. Файловые системы, Inodes и Ссылки (Symlinks vs Hardlinks)

## 3. Глубокое погружение: Inodes, Жесткие (Hardlink) и Символические (Symlink) ссылки

Чтобы навсегда понять разницу, нужно посмотреть, как файл физически устроен в Linux.

---

### 🧩 Анатомия файла в Linux

Файл в Linux состоит из трех уровней:
1. **Запись в директории (Имя):** Таблица, связывающая имя файла с номером Inode (`file.txt` ➔ Inode #12345).
2. **Inode (Метаданные):** Хранит размер, владельца, права, время доступа и **счетчик ссылок (Links Count)**.
3. **Блоки данных (Data Blocks):** Физические секторы на диске с байтами текста/видео.

---

### 🔗 1. Жесткая ссылка (Hard Link)

**Жесткая ссылка** — это просто **еще одно имя для того же самого Inode**.

```bash
# Создание жесткой ссылки:
ln original.txt hardlink.txt
```

#### Как это выглядит под капотом:
```
Директория:
  "original.txt"   ──┐
                     ├──> [ Inode #55555 ] ──> [ Блоки данных: "Hello World" ]
  "hardlink.txt"   ──┘    (Links count: 2)
```

#### Особенности и поведение:
* `original.txt` и `hardlink.txt` имеют **одинаковый номер Inode** (проверяется через `ls -i`).
* Если изменить содержимое `hardlink.txt`, оно изменится и в `original.txt` (ведь данные на диске одни и те же!).
* **Удаление оригинала:** Если выполнить `rm original.txt`, файл **НЕ удалится с диска**! Счетчик ссылок у Inode уменьшится с 2 до 1. Данные будут жить, пока существует хотя бы одна жесткая ссылка.
* **Ограничения:**
  1. Нельзя создавать между разными дисками/разделами (Inode уникален только в пределах одной файловой системы).
  2. Нельзя создавать на директории (защита от бесконечных рекурсивных циклов в ОС).

---

### 🔀 2. Символическая ссылка (Symbolic Link / Symlink / Soft link)

**Символическая ссылка** — это самостоятельный файл-ярлык, который содержит внутри себя **текстовый путь** к целевому файлу.

```bash
# Создание символической ссылки (флаг -s):
ln -s /var/log/nginx/access.log my_log_link
```

#### Как это выглядит под капотом:
```
"my_log_link" ──> [ Inode #99999 ] ──> [ Текст: "/var/log/nginx/access.log" ]
                                                        │
                                                        ▼
"access.log"  ──> [ Inode #55555 ] ──> [ Блоки данных с реальными логами ]
```

#### Особенности и поведение:
* У симлинка **свой собственный Inode**.
* Симлинк весит ровно столько байт, сколько символов в пути к файлу (например, 28 байт).
* **Удаление оригинала:** Если удалить целевой файл `access.log`, симлинк останется, но станет «битым» (Dangling / Broken symlink). При попытке прочитать его будет ошибка `No such file or directory`.
* **Преимущества:**
  1. Может указывать на файлы на **других дисках и сетевых хранилищах**.
  2. Может указывать на **директории** (`ln -s /var/log /opt/logs`).

---

### 📊 Сравнительная таблица (Шпаргалка для собеседования)

| Критерий | Жесткая ссылка (Hardlink) | Символическая ссылка (Symlink) |
| :--- | :--- | :--- |
| **Команда создания** | `ln file link` | `ln -s file link` |
| **Номер Inode** | **Одинаковый** с оригиналом | **Свой собственный** отдельный Inode |
| **Что если удалить оригинал?** | Данные доступны через ссылку, пока есть ссылки | Ссылка ломается (битый ярлык) |
| **Работа между разными дисками/ФС** | ❌ **Нет** (только внутри одной ФС) | ✅ **Да** (любые диски и сетевые папки) |
| **Можно ссылаться на папки?** | ❌ **Нет** | ✅ **Да** |
| **Размер ссылки** | Такой же, как у оригинала (смотрит на те же блоки) | Размер строки с путем (несколько байт) |

### 🚀 Реальные примеры применения в DevOps и продакшене

1. **Nginx: Включение/выключение сайтов (`sites-available` vs `sites-enabled`):**
   * Все конфиги лежат в `/etc/nginx/sites-available/`.
   * Чтобы включить сайт, создают симлинк:
     `ln -s /etc/nginx/sites-available/mysite.conf /etc/nginx/sites-enabled/`
   * Чтобы отключить: `rm /etc/nginx/sites-enabled/mysite.conf` (исходный файл не теряется).

2. **Zero-Downtime Deployments (Атомарное переключение релизов):**
   * В директории лежат релизы: `/app/releases/v1.0` и `/app/releases/v2.0`.
   * Сервис работает с путем `/app/current` (который является симлинком).
   * При деплое новой версии симлинк атомарно переключается на новый релиз:
     `ln -sfn /app/releases/v2.0 /app/current` ➔ мгновенный переход без остановки приложения!

3. **Экономия места при инкрементальных бэкапах (Rsync, Borg, Time Machine):**
   * Если файл не менялся со вчерашнего дня, утилита бэкапа не копирует его заново, а создает **Hardlink** на вчерашнюю копию. Бэкап за 30 дней занимает место как за 2 дня!

4. **Включение сервисов в systemd:**
   * Команда `systemctl enable nginx` просто создает симлинк из `/lib/systemd/system/nginx.service` в `/etc/systemd/system/multi-user.target.wants/`.

## 4. Жизненный цикл процессов и Состояния (Process States)

Когда ОС запускается, ядро стартует процесс **PID 1 (`systemd` или `init`)**, который является предком всех остальных процессов в системе.

### Системные вызовы при создании процесса:
1. `fork()` — клонирует текущий процесс (создает точную копию).
2. `execve()` — заменяет тело скопированного процесса новой программой.

### Состояния процессов (Столбец `STAT` в выводе `ps aux` / `top`):
* **`R` (Running / Runnable):** Процесс выполняется на CPU прямо сейчас или ждет своей очереди к процессору.
* **`S` (Interruptible Sleep):** Процесс спит, ожидая события (сетевого пакета, ввода пользователя). Легко прерывается сигналами.
* **`D` (Uninterruptible Sleep):** Процесс заблокирован в ожидании дискового ввода-вывода (I/O). **Не реагирует даже на `kill -9`!** Если таких процессов много, растет Load Average и `%wa` в `top`.
* **`Z` (Zombie / Defunct):** Процесс завершился, но его родительский процесс не прочитал его код завершения через `wait()`. Зомби не потребляет CPU и RAM, но **занимает слот в таблице процессов (PID)**.
* **`T` (Stopped):** Процесс остановлен сигналом (например, нажатием `Ctrl+Z` в терминале).

## 5. Сигналы процессов (Signals)

Сигнал — это способ ядра или пользователя асинхронно уведомить процесс о событии.

| Номер | Имя | Что делает | Можно перехватить? |
| :--- | :--- | :--- | :--- |
| **1** | `SIGHUP` | Перечитать конфигурацию без перезапуска службы | Да (используется для Nginx/Prometheus reload) |
| **2** | `SIGINT` | Прерывание с клавиатуры (`Ctrl+C`) | Да |
| **9** | `SIGKILL` | Принудительное мгновенное уничтожение процесса ядром | **НЕТ** (ядро убивает процесс безусловно) |
| **15** | `SIGTERM` | Запрос на корректное завершение (Graceful Shutdown) | Да (процесс закрывает сокеты и БД перед выходом) |

## 6. Виртуальная память, Буферы и Кэш

Каждому процессу кажется, что у него есть вся память компьютера (Виртуальное адресное пространство). Ядро делит память на **страницы (Pages)** размером 4 КБ и проецирует их на физическую память (RAM) через таблицу страниц.

### Память `buff/cache` (Buffer & Cache):
* **Page Cache:** Неиспользуемая память RAM автоматически выделяется ядром под кэш прочитанных с диска файлов. Если приложению срочно нужна память, ядро моментально освобождает кэш.
* **Swap (Подкачка):** Сброс редко используемых страниц памяти на медленный диск, когда физической RAM начинает не хватать.
