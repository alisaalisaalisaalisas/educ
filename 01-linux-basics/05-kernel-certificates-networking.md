## 🔐 1. SSL/TLS Сертификаты (Must Know для дежурного)

Протухший SSL-сертификат на проде — это мгновенная авария P1/Sev1 (пользователи видят страшную красную плашку «Подключение не защищено»).

### Как устроен сертификат:
* **Private Key (`privkey.pem`):** Секретный закрытый ключ сервера. Никому не передается!
* **Public Certificate (`cert.pem`):** Открытый сертификат для домена.
* **Certificate Chain (`fullchain.pem`):** Цепочка доверия (Сертификат сервера ➔ Промежуточный CA ➔ Корневой Root CA). Браузер доверяет сайту только при полной цепочке!

### Шпаргалка по командам OpenSSL:
```bash
# 1. Проверить срок действия SSL-сертификата удаленного сайта (без браузера)
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null | openssl x509 -noout -dates

# 2. Посмотреть подробную информацию (кем выдан Issuer, домены Subject Alternative Name)
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null | openssl x509 -noout -issuer -subject -ext subjectAltName

# 3. Проверить локальный файл сертификата на диске
openssl x509 -in /etc/ssl/certs/my_cert.crt -text -noout

# 4. Проверить, подходит ли Private Key к сертификату (сравнить их md5 хеши)
openssl x509 -noout -modulus -in cert.crt | openssl md5
openssl rsa -noout -modulus -in privkey.key | openssl md5
# Хеши ДОЛЖНЫ совпадать!
```

### Как мониторят SSL в Prometheus:
Экспортер `blackbox_exporter` опрашивает сайты и отдает метрику `probe_ssl_earliest_cert_expiry`. Алерт настраивается за **14–30 дней** до истечения:
```promql
(probe_ssl_earliest_cert_expiry - time()) < (86400 * 14)
```

## ⚙️ 2. Ядро Linux (Kernel) и виртуальные файловые системы

### Пространство ядра vs Пространство пользователя:
* **Kernel Space (Ядро):** Управляет железом (CPU, память, диски, сеть), драйверами и системными вызовами (syscalls).
* **Userspace (Пользовательское пространство):** Где работают наши программы (Nginx, Docker, Python, Bash).

### Виртуальная ФС `/proc` (Все о процессах и ядре «на лету»):
Файлы в `/proc` не занимают места на диске — это интерфейс прямого чтения структур памяти ядра.

```bash
# Информация о процессоре и ядрах
cat /proc/cpuinfo

# Детальная статистика по памяти
cat /proc/meminfo

# Текущий Load Average
cat /proc/loadavg

# Посмотреть информацию о конкретном процессе по его PID
cat /proc/1234/status          # Память, треды, статус
ls -la /proc/1234/fd/          # Список ВСЕХ открытых файловых дескрипторов процесса
cat /proc/1234/environ         # Переменные окружения процесса
```

### Системные вызовы (Syscalls) и утилита `strace`:
Программы из Userspace не могут напрямую трогать диск или сетевую карту. Они обращаются к ядру через **системные вызовы (System Calls)**:
* `open()` / `openat()` — открыть файл.
* `read()` / `write()` — прочитать / записать данные на диск или в сокет.
* `connect()` / `bind()` — сетевые соединения.

#### `strace` (Рентген для процессов в Linux):
Если программа падает или зависает, но **не пишет ничего в логи**:
```bash
# 1. Запустить программу и посмотреть, какие файлы она пытается открыть
strace -e trace=file nginx

# 2. Подключиться к уже работающему зависшему процессу по PID
strace -p 1234

# 3. Отследить только сетевые вызовы (к каким IP/портам лезет сервис)
strace -e trace=network -p 1234

# 4. Собрать сводную статистику: на каких вызовах процесс тратит больше всего времени
strace -c ls -la
```

---

### Логи ядра (`dmesg`):
Когда падает железо, диск сыплет ошибками (I/O error) или процесс убит по памяти:
```bash
# Читаем буфер сообщений ядра с человеческими датами (-T)
dmesg -T | grep -E -i "oom|error|segfault|ext4"
```

### Тюнинг параметров ядра (`sysctl`):
Параметры хранятся в `/etc/sysctl.conf` или `/etc/sysctl.d/`.
```bash
# Посмотреть все текущие параметры ядра
sysctl -a

# Применить изменения без перезагрузки сервера
sysctl -p

# Важные параметры для продакшена:
# vm.swappiness = 10         # Насколько агрессивно использовать swap (0-100)
# net.ipv4.ip_forward = 1    # Включить маршрутизацию пакетов (нужно для Docker/K8s)
# fs.file-max = 2097152      # Максимальное число открытых файлов в системе
```

## 📄 3. «Всё есть файл», Файловые дескрипторы и Ошибка «Too many open files»

В Linux файлы, сетевые сокеты, каналы (pipes) и устройства представлены как **файловые дескрипторы (File Descriptors, FD)**.

### Ошибка: `java.io.IOException: Too many open files` или `socket() failed (24: Too many open files)`
* **Что случилось:** Процесс открыл слишком много сетевых соединений или файлов и уперся в системный лимит (`ulimit`).

```bash
# 1. Посмотреть текущий лимит открытых файлов для текущей сессии
ulimit -n

# 2. Подсчитать, сколько файлов сейчас открыто процессом (по PID)
ls /proc/1234/fd | wc -l

# 3. Найти топ процессов по количеству открытых дескрипторов
lsof | awk '{print $1}' | sort | uniq -c | sort -nr | head -n 10
```

### Как исправить:
1. Временно для сессии: `ulimit -n 65535`
2. Постоянно для пользователей в `/etc/security/limits.conf`:
   ```ini
   *    soft    nofile    65535
   *    hard    nofile    65535
   ```
3. Для служб `systemd` в unit-файле (`/etc/systemd/system/app.service`):
   ```ini
   [Service]
   LimitNOFILE=65535
   ```

## 🌐 4. Сетевой стек Linux и Состояния TCP-сокетов

### Состояния TCP-соединений (Частый вопрос на собеседовании):
* **`LISTEN`:** Процесс ждет входящих подключений на порту (например, Nginx слушает 80/443).
* **`ESTABLISHED`:** Сессия активна, идет обмен данными.
* **`TIME_WAIT`:** Клиент закрыл соединение, сокет висит в ожидании (обычно 60 сек), чтобы убедиться, что запоздавшие пакеты не перепутаются.
  * *Проблема:* Если сокетов в `TIME_WAIT` десятки тысяч — закончатся свободные локальные порты (Ephemeral ports).
* **`CLOSE_WAIT`:** Удаленная сторона закрыла соединение, но **наше локальное приложение забыло закрыть сокет** (утечка сокетов / баг в коде разработчика).

```bash
# Подсчет количества TCP-соединений в разных статусах
ss -ant | awk '{print $1}' | sort | uniq -c
```

### Сетевые интерфейсы и маршрутизация:
```bash
# Показать сетевые интерфейсы и их IP адреса
ip addr show (или ip a)

# Проверить таблицу маршрутизации (Default Gateway - шлюз по умолчанию)
ip route show

# Проверить ARP-таблицу (соответствие IP -> MAC адрес)
ip neigh show
```

### Файрволлы в Linux (iptables / ufw / nftables):
Если порт слушается сервисом (`ss -tulpn` видит порт), но снаружи он недоступен:
```bash
# Посмотреть правила iptables
iptables -L -n -v

# Статус простого файрвола UFW (Ubuntu)
ufw status
```
